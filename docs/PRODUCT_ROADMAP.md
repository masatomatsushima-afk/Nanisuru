# Nanisuru プロダクトロードマップ（最終目標）

このドキュメントは Nanisuru が将来的に目指す姿（最終目標）と、現在のMVPで何を優先しているかを
整理したものです。**現時点ではドキュメントのみで、実装は行いません。** 各項目に着手する際は、
このロードマップを参照しつつ、まず `docs/NANISURU_MVP_RULES.md` の制約（赤エラー禁止・大規模リファ
クタ禁止・まだ戻さない機能）を確認してから進めてください。

対象読者: Cursor（このリポジトリで作業するAIエージェント）と開発者本人。

## 1. 最終目標（プロダクトビジョン）

Nanisuru は最終的に、**世界中・日本全国どこでも使えるAI旅行プランアプリ**を目指します。
現在はMVP（Lightweight MVPモード）で最小限の安定動作を優先していますが、将来的には以下まで
機能を広げます。

### 1.1 世界中・日本全国対応

- 韓国・東京・大阪だけでなく、福岡・札幌・沖縄・Paris・Bangkok・New York・Melbourne など
  あらゆる地域に対応する。
- destination（目的地）外のスポットを絶対に混在させない（destination lock）。
- 都市が有名かどうかに関わらず、小さな地方都市・馴染みの薄い町でも使える。
- 現状: `src/lib/destination-safety.ts` の `normalizeDestination()` により、固定の都市リストに
  依存しない汎用的な destination lock を実装済み（MVPで対応済み・継続強化）。

### 1.2 高精度スポット提案（Google Places / Maps API 連携）

- OpenAIだけにスポット名を考えさせない。将来的には Google Places API / Google Maps API から
  実在する候補（店名・座標・評価など）を取得する。
- 人気店・穴場・ローカル店・カフェ・夜景・体験などをカテゴリ分類する。
- 評価（rating）、口コミ数、営業時間、現在地からの距離、写真などの実データを判断材料に使う。
- AIの役割は「ゼロから店名を創作する」ことではなく、「取得済みの実在候補を条件に合わせて
  最適な順番・組み合わせに並べる」ことに変わる。
- 現状: MVPでは `placeName` / `category` / `popularityType` / `confidence` フィールドと
  最小限の安全エリア一覧（`KNOWN_CITY_REGISTRY`）でスポットの具体性を上げているが、
  実際の Google Places API 連携はまだ行っていない。

### 1.3 Google Maps連携の強化

- 現在の文字列ベースの `mapsQuery` から、将来的には Google Places の `placeId` / 緯度経度
  （coordinates）ベースに置き換え、検索の曖昧さそのものを無くす。
- 目的地外の検索結果に絶対にならないようにする（destination lock の思想を維持したまま強化）。
- 現在地からの道案内、徒歩・電車・車・タクシーなど複数の移動手段候補、所要時間表示、
  複数スポットを回る際のルート最適化に対応する。
- 現状: `mapsQuery` / `socialQuery` / `isSpecificPlace` による destination スコープ済み検索
  クエリ止まり（`src/lib/concierge-links.ts`）。`placeId` 化・ルート最適化は未着手。

### 1.4 現在地取得の活用

- ユーザーの現在地から近い候補を提案できるようにする。
- 「旅行中に今から近くで行ける場所」をその場で提案する機能。
- 位置情報の取得が拒否されてもアプリ自体は壊れず、通常通り使える（現状も同様の思想で実装）。
- 現在地が無くても、目的地ベースだけでプラン生成・利用が完結できることを常に維持する。

### 1.5 予約機能

- レストラン予約、アクティビティ予約に対応する。
- ホテル周辺の候補提案。
- まずは外部予約サイトへの連携（検索・遷移）から始め、将来的にはアプリ内予約導線を目指す。
- 予約済みの予定をプランに反映できるようにする（時間帯の重複回避など）。
- 現状: 未着手（MVPでは明示的に対象外）。

### 1.6 AI旅行秘書（チャットベースの部分編集）

- 旅行ごとの専用チャットで、プラン全体ではなく**一部だけ**を自然言語で編集できるようにする。
  - 例:「雨やから予定変えて」
  - 例:「このカフェだけ変えて」
  - 例:「予算下げて」
  - 例:「今近くで行ける場所にして」
  - 例:「夜ご飯だけ人気店に変えて」
- プラン全体の再生成ではなく、指示された範囲だけをピンポイントで更新することが重要。
- 現状: `src/app/(tabs)/ai.tsx` はMVP仮画面で、本番API接続は未実装（意図的に後回し）。

### 1.7 服装・持ち物提案の高度化

- 天気・季節・目的地・その日の予定内容から、テンプレ化しない具体的な提案を行う。
  - 例: 7月なら暑さ・汗・日差し・冷房対策
  - 例: 冬なら防寒
  - 例: 雨予報なら折りたたみ傘・防水靴
  - 例: ビーチ・夜景・高級ディナーなど、予定内容に応じた服装
- 「羽織りがあると安心」のような、どの季節でも言える決まり文句は禁止する。
- 現状: `src/lib/outfit-packing-advice.ts` で天気・季節・目的地・行程内容ベースの提案ロジックを
  実装済み（継続改善対象）。

### 1.8 保存・思い出機能

- 作成したプランを保存できる。
- 旅行ごとのフォルダで管理できる。
- 写真・動画をプランに紐づけられる。
- 後から思い出として見返せる。
- 友達や恋人とプランを共有できる。
- 現状: MVPでは軽量化のため Supabase 保存の本格実装は意図的に無効化中（`LIGHTWEIGHT_MVP`）。

### 1.9 Discover（他ユーザーのプラン発見）

- 他のユーザーが作成したプランを閲覧できる。
- 人気プラン、カップル向け、友達向け、ひとり旅向けなどのカテゴリ分け。
- 保存・いいね・フォロー機能。
- 現状: MVPでは重い読み込み（Supabase全件取得など）を意図的に無効化中（`LIGHTWEIGHT_MVP`）。

## 3. 現在のMVP優先順位

将来の理想像は上記の通りですが、**今のMVP開発では以下の優先順位を守る**（上にあるものほど優先度が高い）。

1. 赤エラーなし（Uncaught Error / Console Error を新たに出さない）
2. Plan Form から Plan Detail まで確実に到達できる
3. destination外のスポットを出さない（destination lock）
4. currency を勝手に変えない（ユーザー選択を保持）
5. arrivalTime / departureTime を守る（1日目・最終日の時間制約）
6. Google Maps 検索が現在地周辺にならない（destination スコープ済みクエリ）
7. 抽象的すぎる item を減らす（具体的なスポット名・エリア名を優先）
8. 服装提案を季節・天気・予定内容に合わせる（テンプレ文言を避ける）

新しい機能（本ロードマップの1〜9）を検討する際も、上記1〜8を壊さないことを最優先にする。
迷った場合は実装を進めず、まずユーザーに確認する。
